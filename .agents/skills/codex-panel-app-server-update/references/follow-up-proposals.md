## Follow-Up Proposals

Evaluate candidates in this order before describing them as proposals:

1. Establish a concrete opportunity from current Panel behavior and the upstream contract: enable or correct an interaction for affected users; simplify internal responsibilities, state, dependencies, or exception paths without changing visible behavior; or remove genuinely obsolete features or compatibility work. Check the conditions that make the change relevant, including managed deployments rather than only the repository owner's usage. A new API name or ease of implementation alone does not establish value.
2. Trace the relevant current paths and compare them with the proposed behavior or architecture: what becomes possible, what is removed, what is added, and which maintenance work becomes easier. Check whether existing Codex or Obsidian functionality already serves the need sufficiently before adding a Panel surface. Existing UI does not prove that a new request is handled under its actual conditions, and unchanged UI does not rule out internal improvement. Apply `docs/design.md`: keep Panel thin and leave runtime semantics and state with Codex.
3. Resolve unknowns that could change a recommendation or rejection using relevant source, contracts, or focused validation. Missing evidence is not evidence of no value; if a material question cannot be resolved, state the uncertainty without presenting an unsubstantiated proposal. Bound investigation by plausible relevance and consequence, not an exhaustive audit of every new capability.
4. Retain only candidates whose demonstrated benefit justifies implementation, ongoing maintenance, and compatibility risks, including the impact of removals on supported users. If none pass, report no proposals as a normal outcome; do not manufacture deferred ideas to fill the list.

For a UI candidate, inspect the relevant feature, state, host, component, and styling paths before proposing a design. Establish how it fits current interactions, Preact composition, Obsidian-native patterns, and Panel display conventions. Release notes or generated bindings alone are not sufficient evidence.

Explain each proposal in familiar action and behavior terms: current behavior or maintenance burden → proposed behavior or structure → benefit and cost. Include the integration point, prerequisites, and remaining uncertainty needed to judge it. Use protocol names and generated diffs as supporting evidence, not as the explanation. Rank multiple proposals by concrete user or maintenance benefit and cost. Keep optional follow-ups separate from required compatibility work.
